## What it steers

criteria 3 and 4). Slice 4 (2026-10-17) enforces the two rows below in code: the record carries

the record runs the narrowed pair. The floor-band row reads claim 7's cycle-phase study, so the
ceiling moves when that study is re-run, not when this sheet is edited.

## Forward tests to register

Forward-test rows live only in the event lane's own fragment (`docs/research/forward-tests/<event-id>.md`,
written by the lane that owns `events/<event-id>.md`). This doc writes none. Each row below is a
proposal for that lane to register at its next pass, at the next free id in that fragment.

**How a proposal reaches the lane** (2026-10-27): each row's token is `ai-dip-2026-10/<Id>`. Until
that token appears in the event's fragment (registered) or its ledger (declined, with why), the
event's next pulse cannot be screened without a session (`scripts/conviction-proposals.mjs`;
`docs/process/EVENT-RESEARCH.md` → *Conviction proposals*). A row with no Id is a citation.

**How a scored row scores its claim** (2026-10-27): `npm run research:claims` reads the registered
row's Outcome on the claim's own day, against the claim's falsifier. P1 decides 2b, and
`FT-nvda-2026-11-18-print-3` decides 5: a pass holds the claim, a kill fails it. P1 also bears on 9
(the table's Claim column) as evidence, never as its score: 9's falsifier is about straddles. P2
decides 9 only on a pass, since one print inside its straddle is one of the three the falsifier
needs, so a killed P2 leaves 9 pending until the next two prints are read. **P6 reads
inverted:** its prediction is claim 4's falsifier, so P6 passing fails claim 4. Until a row is
registered and scored, its claim reads pending. **Who runs it** (2026-10-27): the event lane that
scores a row runs `npm run research:claims -- --event <its-event-id>` in the same PR, scores only
(`docs/process/EVENT-RESEARCH.md` → *Conviction claims*). That reaches every claim due on a
registered row's day. Claim 1 is scored by a study re-run, so it waits for a full pass.

**Claims 1 and 2a are scored against the claim, not the call** (2026-10-30). Their rows'
falsifiers above are the house call's: they name what would prove *standing aside* wrong. A claim's
falsifier proves the *claim* wrong (`src/playbooks/claim-score.ts`), so the record carries the
inverse. Claim 2a fails if any of the three pre-print puts finishes in the money: a CRWV close under
$54 on 11-06 fails it on its own. A close at or above $54 leaves it pending, because the next 2 puts
(the ~Feb and ~May 2027 prints) have no strike yet. It is a price check, so the lane pass that
scores any of this conviction's rows after 11-06 reads it off the tape.

## What this first instance taught the format (for slice 2)

- **A claim can cut against its owner.** Claim 7 says the near-term downside isn't finished.
  The format has to carry claims that argue against the view, or it only launders it.
- **One falsifier per row.** "Puts before, calls after" had two halves with different evidence
  and dates, so it became 2a and 2b. The data type should hold one falsifier per claim.
- **A claim that is already a playbook's evidence steers nothing new.** Claim 5 needs a pointer
  to S1-NVDA's study rather than a second weight. Otherwise one result counts twice.
- **The check is per pair today; the stance is aggregate.** #4469's check reads each
  subscription's own net P/L. Eric's stance judges the pairs together. Slice 2 has to pick one,
  and the stance says aggregate.
- **A check date can gate a pair whose evidence is a study.** If criterion 5 gates S1-NVDA on
  2027-01-29, S1's next entry (about 20 sessions before a ~2027-02-24 print, so ~01-26) opens
  before the check anyway. Proposal: a conviction gates only pairs running *as* conviction and
  cites the rest.
- **The lint needed one more directory.** `research:lint` now reads `docs/research/convictions/`
  with the same call-sheet contract. Owner, horizon, risk stance, check date and steered pairs
  aren't linted. They belong in slice 2's type.
