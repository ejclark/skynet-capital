### Why nothing caught it

`node scripts/event-scan.mjs --validate` enforces `duplicate id` — and both ids are unique, so it
passes. Nothing anywhere checks for **duplicate events under distinct ids**. The lane's own dedupe
key is the branch name `research/<event-id>`, which is derived from the id, so two ids for one event
defeat it by construction rather than by accident.

This is the **same failure class** as the `FT-25` collision banked in `docs/LESSONS.md` on
2026-09-04, where two unrelated sessions each registered a forward test under the same bare number.
`.github/prompts/event-research.md` fixed that one by namespacing new forward-test ids to the
session's own assigned event — the principle being that a parallel leg must derive a shared-register
key from *the one thing it owns exclusively*. Event ids are the same register with the same defect
and no such rule: a sweep that **discovers** an event coins its slug freely, and free-text slugs
from independent sessions collide by describing rather than by identifying.

### The process finding — id collision, and why the existing guard could not see it

The defect: **`event-scan.mjs --validate` enforces unique ids and nothing enforces unique events.**
Two sibling adjacency sweeps found one Waller slot seven minutes apart on 2026-09-01, coined
`fed-waller-outlook-…` and `waller-economic-outlook-…` from the same primary page, and both survived
validation because both slugs are unique. The lane's dedupe key — the branch `research/<event-id>` —
is derived from the id, so it cannot see the collision either. The cost this time was one wasted
session and a calendar entry that double-counts the 09-03 corridor; the cost next time is a *live*
event researched twice in parallel under two slugs, two stances, and two ledgers that can disagree.

**Same class as the `FT-25` collision** banked in `docs/LESSONS.md` on 2026-09-04.
`.github/prompts/event-research.md` repaired that one by namespacing new forward-test ids to the
session's own assigned event — a parallel leg derives a shared-register key from the one thing it
owns exclusively. Event ids are the same shared register with the same defect and no equivalent rule:
a discovering sweep coins a **descriptive** slug, and independent descriptions of one thing collide.

**The shape of a fix, proposed and deliberately not built here.** A duplicate-event check belongs in
`scripts/event-scan-validation.mjs` beside the duplicate-id check, but it is not a five-line
addition and should not be improvised from inside a research lane. Same-date, same-kind events are
*normal* on this calendar — 09-03 alone legitimately carries Challenger 07:30, Waller 08:30, ISM
Services 10:00 and Hammack 15:00 — so a naive date+kind rule would fire on all of them, and a title
similarity threshold that separates "Waller" from "Hammack" while catching "fed-waller-outlook" vs
"waller-economic-outlook" needs a test suite and a tuned threshold, not a guess. The cheaper and
sharper candidate is to key on the **source line**: two `estimate` entries citing the *same primary
URL* for the *same date* are near-certainly one event, which is exactly this case and is not true of
the four legitimate 09-03 siblings. Either way it is the scanner's owner's call.

**Routed here rather than patched mid-flight**, and that is a deliberate choice, not a dodge. Roughly
six sibling event sessions are appending to `docs/LESSONS.md`, `docs/IDEAS.md` and
`forward-tests.md` in parallel today; appending to a shared file to report a parallel-session
collision would risk causing one. The canonical Waller close-out set this precedent explicitly when
it declined to renumber `FT-25` mid-flight. This ledger is durable, discoverable and owned solely by
this session, so the finding lives here and is surfaced in the PR body.

**The calendar entry is annotated, not deleted.** `market-events-data.ts`'s
`fed-waller-outlook-2026-09-03` note now opens with the duplicate finding and points at the canonical
id. Deleting the entry would silence the scanner just as effectively and erase the evidence that the
collision happened, which is the only durable value this id has; and with both entries now past and
closed, a duplicate costs nothing forward beyond the corridor-density warning already carried in the
signals list above.
